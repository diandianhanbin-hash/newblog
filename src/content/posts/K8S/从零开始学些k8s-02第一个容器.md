## 背景

`Web`应用是我们最常用的一个应用，我们用一个`nginx`镜像来练手。

## 开始

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
spec:
  containers:
  - name: nginx
    image: nginx:1.7.9
    ports:
    - containerPort: 80
```

保存为`firstweb.yaml`后执行：

```yaml
kubectl create -f firstweb.yaml
>>
deployment.apps/nginx-pod created
```

这个时候，`k8s`就开始执行整体的调度任务。调度成功，则可以看到

```yaml
kubectl get pods
NAME                                READY   STATUS    RESTARTS   AGE
nginx-pod                           1/1     Running   0          13s
```

容器已经成功跑起来了。

## 指标含义

这是一个非常简单的配置文件。

apiVersion `api`的版本号，默认写v1即可，有些时候也会用app/v1

kind 我们这里部署的是`pod`，所以使用`pod`，还有`deployment`，`service`等。这个指标指定了部署的类型。

metadata 这里用kv的形式标识了这个`pod`的一些元信息，用于查询，分类等。

spec 这个表示我们期望这个对象的状态。这里我们期望这个对象是一个容器，因此指定了`containers`，`containers`里面都声明了这个容器的名称，使用的镜像，暴露的端口等信息。

## 升级这个web镜像
我们在开发过程中，经常会有更新镜像的需求。这个操作在k8s上是非常容器的。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
spec:
  containers:
  - name: nginx
    image: nginx:1.8
    ports:
    - containerPort: 80
```

把`firstweb.yaml`文件的`image`直接改成`1.8`版本的`nginx`，然后执行

```yaml
kubectl apply -f firstweb.yaml 
>>
pod/nginx-pod configured
```

我们通过事件可以看到具体的变更过程。

```yaml
kubectl describe pod nginx-pod
...
Events:
  Type    Reason     Age                From               Message
  ----    ------     ----               ----               -------
  Normal  Scheduled  19m                default-scheduler  Successfully assigned default/nginx-pod to minikube
  Normal  Pulled     19m                kubelet            Container image "nginx:1.7.9" already present on machine
  Normal  Killing    42s                kubelet            Container nginx definition changed, will be restarted
  Normal  Pulling    42s                kubelet            Pulling image "nginx:1.8"
  Normal  Created    33s (x2 over 19m)  kubelet            Created container nginx
  Normal  Started    33s (x2 over 19m)  kubelet            Started container nginx
  Normal  Pulled     33s                kubelet            Successfully pulled image "nginx:1.8" in 9.090583805s
```

这里可以很清楚的看到，原来的`pod`被重建成`1.8`版本的`nginx`镜像了。

```yaml
kubectl get pod nginx-pod --output=yaml
...
containerStatuses:
  - containerID: docker://98ff0a9fc9e88f1043f2729fc26bfc8997bc03b8ffb424b07b956f9c429affd1
    image: nginx:1.8
```

## 这样设计的好处

我们只描述这个对象的最终状态，而变更的过程，则完全由k8s来完成。

> 这样的操作方法，是Kubernetes“声明式API”所推荐的使用方法。也就是说，作为用户，你不必关心当前
的操作是创建，还是更新，你执行的命令始终是kubectl apply，而Kubernetes则会根据YAML文件的内容变
化，自动进行具体的处理。
> 

> 而这个流程的好处是，它有助于帮助开发和运维人员，围绕着可以版本化管理的YAML文件，而不是“行踪
不定”的命令行进行协作，从而大大降低开发人员和运维人员之间的沟通成本
>
