## 背景

我们开发中，会有出现有状态的容器，或者几个容器需要共享一些文件。这个时候就需要关联属主机的目录作为存储卷

## 开始

我们修改之前的`firstweb.yaml`文件。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
spec:
  containers:
  - name: nginx
    image: nginx:1.7.9
    ports:
    - containerPort: 80
    volumeMounts:
    - mountPath: /home
      name: nginx-vol
  volumes:
  - name: nginx-vol
    hostPath: /tmp
```

给这个`nginx`的镜像挂载一个`/home`的目录，挂载到属主机上。我们进入容器写两个文件到对应的目录上

```shell
touch test.py
echo '111' > debug.txt
```

然后我们到宿主机的对应目录下就可以看到这两个文件。

```shell
[root@VM-centos] /tmp]# ls -lrt
total 4
-rw-r--r-- 1 root root 0 Oct 23 10:36 test.py
-rw-r--r-- 1 root root 4 Oct 23 10:48 debug.txt
```

说明这两个文件已经持久化到宿主机了，因此如果其他容器也用同样的路径挂载这个目录，那么出现的效果就是两个容器公用这个目录，下面的文件也将会是共用的情况。

- 一个特殊的说明

如果你和我一样，用的是`minikube`搭建的学习环境，而不是用二进制搭建的环境，你会发现，在宿主机的`/tmp`目录下压根找不到你在容器内创建的文件。这是因为`minikube`是通过`docker`构建的环境，因此真实的路径其实是在这个地址。

```shell
/var/lib/docker/overlay2/8f5cacd0f59b99aa9d5f9bb4f24e6451127677da717af2b4d5f69d4f5a910f2f/diff/tmp
```

这是我的地址，你可以用`root`用户通过`find / -name 'test.py'`这个命令来找到你机器上的真实地址。

当然，最简单的验证办法就是把这个`pod`删了再重建一个一样的，看看这几个文件是否存在即可。

## 挂载地址已有文件

上面展示的是容器内的路径是空文件，如果是有文件的容器会发生什么呢？我们修改一下`firstweb.yaml`的文件内容如下。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
spec:
  containers:
  - name: nginx
    image: nginx:1.7.9
    ports:
    - containerPort: 80
    volumeMounts:
    - mountPath: /etc/nginx/conf.d
      name: nginx-vol
  volumes:
  - name: nginx-vol
    hostPath: /tmp
```

我们使用的是`nginx`镜像，因此`/etc/nginx/conf.d`这个目录下原来放的是`nginx`的配置文件。

在我们使用了刚刚写入两个文件的目录作为`hostPath`挂载后。发生了这样的情况。

```shell
root@nginx-pod:/etc/nginx/conf.d# ls -lrt
total 4
-rw-r--r-- 1 root root 0 Oct 23 02:36 test.py
-rw-r--r-- 1 root root 4 Oct 23 02:48 debug.txt
```

可以看到。容器内的目录被宿主机的目录覆盖了。

## 其他支持的类型

本文使用的是`hostPath`的方式绑定了宿主机的地址，事实上，`k8s`还支持了其他方式，可以参考[Kubernetes API Reference Docs](https://kubernetes.io/docs/reference/generated/kubernetes-api/v1.22/#volume-v1-core) 查看其他的挂载方式。

## 注意点

在使用`hostPath`的时候需要特别注意，我们的演示实例是非常简单的实例，也是单机的模式，事实上在生产上的应用中，`k8s`会随机把我们的这些`pod`调度到任意的一台`worker`机器上，你的应用如果对宿主机的这个地址有依赖，那么可能会导致`k8s`调度到某些`workder`机器的时候发生应用异常的情况。`
